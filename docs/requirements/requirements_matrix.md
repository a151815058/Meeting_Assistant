# 需求追溯矩陣 (Requirements Traceability Matrix)

本文件為 Meeting_Assistant 專案的 SSDLC 需求分析交付物。所有功能需求（FR）、
安全需求（SR）皆有唯一 ID，並追溯到設計元件、實作模組與測試案例，確保
「需求 → 設計 → 實作 → 測試」全程可追蹤，符合 SSDLC 稽核要求。

狀態欄位定義：`未開始` / `進行中` / `完成` / `延後（見風險登記）`

---

| Risk-ID | 描述 | 影響 | 因應對策 |
|---|---|---|---|
| RISK-01 | MVP 階段的「發言人辨識」（REQ-09）僅能用 VAD+語者分離做聲紋聚類（Speaker A/B），無法保證 100% 對應到真實與會者身分；真正的平台原生說話事件（REQ-10）需要 Bot 加入會議（Teams Graph Calling API / Google Meet Media API），屬高門檻的未來擴充 | 逐字稿的「發言人」欄位在 MVP 階段準確度有限，需使用者事後校正或語音註冊比對 | 資料模型已預留 `platform_speaker_id`（nullable）欄位；Phase 6 上線後可直接以原生事件覆蓋/強化聚類結果，UI 呈現時優先顯示 `platform_speaker_id`，其次才顯示聚類標籤 |
| RISK-02 | Google Meet Media API 目前為受限預覽/企業限定，Microsoft Graph Calling Bot 需要 Azure Bot 註冊與合規審查，兩者開發與審核週期長 | Phase 6 時程不確定 | Phase 6 列為獨立里程碑，不阻塞 MVP（Phase 0-5）交付 |
| RISK-03 | 瀏覽器端錄音僅能擷取「使用者本機」聽到的聲音（麥克風/分頁音訊），非會議平台端的乾淨多軌音訊，可能影響 VAD/ASR/語者分離準確度 | 轉錄品質與語者分離準確度可能低於 Bot 直接取得媒體流的方案 | 於 README 標示為已知限制，並於 UI 提示使用者以耳機/獨立麥克風降低串音 |
| RISK-04 | LLM 產生會議記錄時，逐字稿內容可能包含意圖操縱 prompt 的文字（prompt injection） | 會議記錄可能被誤導 | REQ-33：逐字稿以資料標籤包裝並防止標籤跳脫、系統提示禁止執行其中指示；寄出前人工複核（REQ-14）。無法 100% 防止，人工複核為最後防線 |
| RISK-05 | Whisper 在 CPU 上的推論速度隨模型大小差異大：本機實測 `medium` 為即時速度的 3 倍慢（RTF 3.0–3.5），會議越長逐字稿延遲越嚴重 | 即時逐字稿延遲、佇列累積 | 預設改用 `small`（RTF 0.82）；`WHISPER_MODEL_SIZE`/`WHISPER_CPU_THREADS` 可調；佇列超過 30 秒音訊時提醒使用者（REQ-26）；需高準確度時建議搭配 GPU 使用 `medium` 以上模型 |
| RISK-06 | 錄音 session 狀態保存於單一 process 記憶體，多個 web worker 時無法共享 | 水平擴充受限 | 目前 Dockerfile 以 gunicorn eventlet `-w 1` 單一 worker 運行；擴充時需改為 sticky session + Redis message queue（`SOCKETIO_MESSAGE_QUEUE`） |
| RISK-07 | 開發模式登入可在不驗證身分下登入任意 Email（含既有 OAuth 使用者）；若誤部署至正式環境等同繞過驗證 | 帳號冒用 | REQ-29：僅 `DevelopmentConfig` 啟用、`ProductionConfig` 恆為關閉且不讀環境變數、正式環境誤開則拒絕啟動、僅接受本機來源請求、每次登入寫入稽核紀錄 |
| RISK-08 | 會議記錄產生工作狀態存於 process 記憶體；伺服器在產生途中重啟時工作中斷，會議狀態停在 `processing` | 需使用者手動重新產生 | 會議記錄頁在無執行中工作時仍提供「產生會議記錄」按鈕，可直接重新產生；多 worker 部署時需改為 Celery（見 RISK-06） |
| RISK-09 | 逐字稿（機密）會傳送至第三方 LLM 服務（Anthropic）處理 | 資料外流至第三方 | 僅在主辦人主動按下「產生會議記錄」時傳送、每次產生皆寫入稽核紀錄；部署前需確認組織的資料處理政策與 Anthropic API 資料使用條款；Provider 介面可抽換為自建模型 |
| RISK-10 | 主辦人可手動新增任意 Email 為與會者（REQ-35），理論上可把本系統當成以自己帳號群發信件的工具 | 垃圾郵件／誤寄 | 信件一律以主辦人本人帳號寄出（責任可追溯，等同主辦人自行寄信）；收件人上限 `MAIL_MAX_RECIPIENTS`、寄出前確認對話框列出全部收件人、重寄冷卻時間（REQ-37）；與會者異動與每次寄送皆寫入稽核紀錄（含收件人清單） |
| RISK-11 | 寄信 API 在連線中斷時無法得知信件是否已送達 | 重試可能造成重複寄送；不重試可能漏寄 | 連線錯誤不自動重試，頁面提示「信件可能未寄出，請確認寄件備份後再決定是否重試」；僅在服務明確拒絕（429／503）時自動重試（REQ-17） |
| RISK-12 | 開發模式本機信箱（REQ-36）的 .eml 檔含會議記錄內容，以明文存於本機 `instance/outbox/` | 本機資料外洩 | 僅開發環境可啟用、正式環境誤開拒絕啟動；`instance/` 已列入 `.gitignore` 不會進版控；測試用信件請定期清除 |
