# 需求追溯矩陣 (Requirements Traceability Matrix)

本文件為 Meeting_Assistant 專案的 SSDLC 需求分析交付物。所有功能需求（FR）、
安全需求（SR）皆有唯一 ID，並追溯到設計元件、實作模組與測試案例，確保
「需求 → 設計 → 實作 → 測試」全程可追蹤，符合 SSDLC 稽核要求。

狀態欄位定義：`未開始` / `進行中` / `完成` / `延後（見風險登記）`

---

## 已知限制與風險登記（Risk Register）

| Risk-ID | 描述 | 影響 | 因應對策 |
|---|---|---|---|
| RISK-01 | MVP 階段的「發言人辨識」（REQ-09）僅能用 VAD+語者分離做聲紋聚類（Speaker A/B），無法保證 100% 對應到真實與會者身分；真正的平台原生說話事件（REQ-10）需要 Bot 加入會議（Teams Graph Calling API / Google Meet Media API），屬高門檻的未來擴充 | 逐字稿的「發言人」欄位在 MVP 階段準確度有限，需使用者事後校正或語音註冊比對 | 資料模型已預留 `platform_speaker_id`（nullable）欄位；Phase 6 上線後可直接以原生事件覆蓋/強化聚類結果，UI 呈現時優先顯示 `platform_speaker_id`，其次才顯示聚類標籤 |
| RISK-02 | Google Meet Media API 目前為受限預覽/企業限定，Microsoft Graph Calling Bot 需要 Azure Bot 註冊與合規審查，兩者開發與審核週期長 | Phase 6 時程不確定 | Phase 6 列為獨立里程碑，不阻塞 MVP（Phase 0-5）交付 |
| RISK-03 | 瀏覽器端錄音僅能擷取「使用者本機」聽到的聲音（麥克風/分頁音訊），非會議平台端的乾淨多軌音訊，可能影響 VAD/ASR/語者分離準確度 | 轉錄品質與語者分離準確度可能低於 Bot 直接取得媒體流的方案 | 於 README 標示為已知限制，並於 UI 提示使用者以耳機/獨立麥克風降低串音 |
| RISK-04 | LLM 產生會議記錄時，逐字稿內容可能包含意圖操縱 prompt 的文字（prompt injection） | 會議記錄可能被誤導 | REQ-33：逐字稿以資料標籤包裝並防止標籤跳脫、系統提示禁止執行其中指示；寄出前人工複核（REQ-14）。無法 100% 防止，人工複核為最後防線 |

| RISK-07 | 開發模式登入可在不驗證身分下登入任意 Email（含既有 OAuth 使用者）；若誤部署至正式環境等同繞過驗證 | 帳號冒用 | REQ-29：僅 `DevelopmentConfig` 啟用、`ProductionConfig` 恆為關閉且不讀環境變數、正式環境誤開則拒絕啟動、僅接受本機來源請求、每次登入寫入稽核紀錄 |
